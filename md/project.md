# 바로온장 DEMO — VSCode Codex 개발 지시서

> 버전: 0.1 / 목적: 정부지원사업 시연용 MVP
> 이 문서를 프로젝트 루트의 `project.md`로 복사하여 Codex에 전달한다.

## 0. Codex 작업 원칙

- **이 문서를 단일 기능 범위 기준으로 삼는다.** 명시되지 않은 기능은 임의로 구현하지 않는다.
- 작업 전 현재 프로젝트 구조와 설치 패키지를 확인하고, 기존 코드가 있다면 보존·재사용한다.
- **한 번에 전체 서비스를 만들지 않는다.** 아래 개발 단계별로 구현하고 각 단계가 끝나면 변경 파일, 확인 방법, 미완료 사항을 보고한다.
- 구현 전에 중요한 미결정 사항이 있으면 질문한다. 확정되지 않은 정책을 임의로 확정하지 않는다.
- 코드는 읽기 쉽게 작성한다. 과도한 추상화, 불필요한 라이브러리, 복잡한 디자인 시스템을 피한다.
- 초기 화면 구현은 목업 데이터로 진행한다. 서버/API/DB 연동은 화면이 확인된 뒤 진행한다.
- 한국어 UI를 기본으로 한다. Figma의 확정 프레임을 기준으로 데스크톱 화면부터 구현하고, 공개 상품 페이지는 모바일에서도 편하게 보이도록 한다.

## 1. 서비스 개요

**바로온장**은 전통시장 상인, 특히 건어물 판매자가 복잡한 쇼핑몰 없이 **상품 사진과 기본 정보만으로 모바일 상품 소개 페이지**를 만들고, 구매자가 **전화로 주문**할 수 있게 하는 DEMO 서비스다.

- 상인은 발급받은 **접속 코드**로 로그인한다(일반 회원가입 없음).
- 코드당 **활성 상품 페이지는 최대 1개**다.
- 첫 방문 시 상품 생성 화면, 기존 상품이 있으면 관리 화면으로 이동한다.
- 상품 생성 시 AI로 상품 사진을 **선택한 스타일에 맞게 편집**할 수 있다.
- 화면의 **남은 코인** 표시는 시연용 임시 숫자이며, 실제 지급·차감·잔액 검증은 하지 않는다.
- 완성한 상품 페이지는 고유 공개 URL과 QR코드로 공유한다.
- 구매자는 로그인 없이 상품 페이지를 보고 `tel:` 링크로 전화한다.
- 이번 MVP에서는 상품 수정·판매중지·삭제 기능을 구현하지 않는다.

**핵심 목표:** 화려한 쇼핑몰 제작기가 아니라, 상인이 쉽게 이용하는 단일 상품 페이지 제작·관리 경험을 보여주는 것.

## 2. 범위: 반드시 포함

1. 공개 랜딩 페이지: 서비스 소개 + `시작하기` 버튼
2. 운영자가 사전에 발급한 **단일 접속 코드** 입력 및 서버 검증(일반 회원가입 없음)
3. 코드에 연결된 상품 유무에 따른 자동 분기
4. 상품 생성: 상품 기본 정보 → 사진 및 소개 → 상호/전화번호 → 미리보기 → 발행
5. 선택적 AI 이미지 꾸미기 및 소개글 다듬기(실제 API 연결은 별도 단계)
6. 공개 상품 페이지: 사진, 상품명, 가격, 원산지/중량, 소개 문구, 상호, 전화주문 버튼
7. 고유 공개 URL 및 QR코드 생성·표시
8. **마이페이지**: 발행된 상품이 있으면 해당 상품의 **QR코드만 표시**, 없으면 **`시작하기` 버튼만 표시**
9. 화면에 **남은 코인** 임시 숫자 표시(목업 값; 서버 저장·차감 없음)

**상품 페이지는 코드당 최대 1개**이며, 이번 MVP에서는 발행 후 수정·판매중지·삭제·재발행 흐름을 제공하지 않는다.

## 3. 범위: 이번 DEMO에서 제외

- 일반 회원가입, 소셜 로그인, 고객 계정
- 장바구니, 온라인 결제, 배송/주문/재고 관리
- 여러 상품 동시 운영, 상품 목록형 쇼핑몰
- 상품 발행 후 수정, 판매중지·재개, 삭제 및 재발행
- 마이페이지의 상품 상세 관리, URL 복사, QR 재다운로드 등 부가 기능(추후 결정)
- **코인/토큰 정책 전체**: 지급, 충전, 차감, 잔액 저장, 사용 이력, 결제, 부족 오류
- AI 호출 횟수 제한·과금 정책(별도 운영 검토)
- 디자인 템플릿 다중 선택, 드래그앤드롭 에디터
- 외부 쇼핑몰 연동, 복잡한 통계·마케팅 자동화

## 4. 화면 및 이동 구조

```text
[랜딩 /]
  └─ 시작하기
       ↓
[코드 입력 /enter]
  └─ 서버에서 단일 접속 코드 검증
       ├─ 코드 무효 → 오류 안내
       └─ 코드 유효 → [마이페이지 /mypage]

[마이페이지 /mypage]
  ├─ 발행 상품 없음 → '시작하기' 버튼 → [상품 생성 /builder]
  └─ 발행 상품 있음 → 생성된 QR코드만 표시

[상품 생성 /builder]
  1. 상품 기본 정보
  2. 상품 사진 및 소개(AI 꾸미기/문구 다듬기 선택)
  3. 상호 및 주문 전화번호
  4. 미리보기 → 발행 → [마이페이지 /mypage]

[공개 상품 페이지 /p/:id]
  └─ 상품 정보 + 전화주문 버튼
```

### 화면 그룹(Figma 기준)

- A. 랜딩
- B. 접속 코드 입력
- C. 상품 생성 1·2·3단계 및 미리보기
- D. 마이페이지(상품 없음/QR코드 표시)
- E. 고객용 공개 상품 페이지

### 공통 UI

- Figma에 있는 `남은 코인` 표기는 임의의 고정 숫자로 렌더링한다. 실제 사용량과 연동하지 않는다.
- 데스크톱 디자인을 우선 구현하되 공개 상품 페이지는 모바일 접근성을 고려한다.
- 입력 오류, 로딩, 저장 성공/실패, 코드 인증 실패 상태를 처리한다. **코인 부족 상태는 구현하지 않는다.**

## 5. 발급 코드 및 인증 정책

- 이번 MVP의 접속 코드는 **운영자가 발급하는 단일 코드 1개**만 사용한다. 사용자별 복수 코드 발급·관리 기능은 구현하지 않는다.
- 코드는 외부에 공개하지 않는 **비밀 접속 코드**다. 코드 보유자만 상품 생성 및 마이페이지 접근 권한을 가진다.
- 코드 입력 후 **서버에서 검증**하고 세션을 발급한다. 프런트엔드 코드에 비밀 코드를 하드코딩하거나 브라우저에서 문자열만 비교하지 않는다.
- 비밀 코드는 서버 환경변수 또는 안전한 서버 측 저장소에 보관하고, 클라이언트 번들·공개 상품 데이터·URL에 노출하지 않는다.
- 추측하기 어려운 코드값, 인증 시도 제한, 세션 만료를 적용한다.
- 한 코드로 발행 가능한 상품은 **최대 1개**다. 발행된 상품이 있으면 생성 화면에 재진입해 두 번째 상품을 발행할 수 없도록 **서버에서도 검사**한다.
- 운영 중 코드가 유출되면 서버 측 코드를 교체하고 기존 세션을 무효화할 수 있도록 설계한다.
- **단일 코드는 사용자별 계정이 아니다.** 여러 사람이 코드를 공유하면 같은 마이페이지·상품에 접근한다. 따라서 코드 비공개를 전제로 시연한다.
- 발행 전 임시 저장은 선택 기능이며 이번 MVP에서는 생략 가능하다.

## 6. 상품 생성 규칙

### 6.1 품목 선택

- 초기에는 사전 정의한 소수의 품목만 제공한다. 예: 멸치, 건새우, 마른오징어, 미역.
- 품목별 기본 소개 문구/헤드라인은 로컬 프리셋 데이터에 저장한다.
- 실제 원산지·중량·가격·특징 등 사실 정보는 사용자 입력값만 사용한다.
- 근거 없는 원산지, 품질, 효능, 인증 등을 AI가 임의 생성하지 않는다.

### 6.2 필수 입력(초안)

- 상호명
- 전화번호
- 품목 및 상품명
- 판매 가격
- 원산지
- 중량/규격
- 원본 상품 사진 1장
- 상품 소개/특징(선택 또는 기본 문구 사용)

필수/선택 여부는 실제 Figma 화면을 구현하기 전에 최종 확인한다.

### 6.3 AI 이미지 편집

- 사용자는 원본 상품 사진을 업로드한다.
- **2~3개의 고정된 예시 스타일 이미지**를 보고 스타일을 선택한다.
- 스타일별 프롬프트는 서버에 미리 작성한다. 예:
  - `marble_plate`: 회색 대리석 바닥 + 흰 접시
  - `wood_topdown`: 나무 식탁 위 접시, 90도 탑뷰
- AI 호출 시 업로드한 **원본 이미지를 참조**해 편집한다.
- 스타일 예시 이미지는 정적 에셋이며, 스타일을 누를 때마다 API를 호출하지 않는다.
- 생성된 사진이 실제 상품 외형과 다를 수 있으므로 **원본 사진 사용 옵션**을 항상 제공한다.
- AI로 전체 페이지/레이아웃/HTML/CSS를 생성하지 않는다.
- 이미지 생성은 서버 API에서 실행하며 API 키를 프런트에 노출하지 않는다.
- 생성 요청 중 중복 클릭/동시 요청을 막는다. **코인 차감이나 잔액 검증은 구현하지 않는다.**

### 6.4 AI 문구

- 상품 특징(짧은 문구)과 상품 소개(긴 문구)는 사용자가 직접 입력한다.
- 상품 소개에는 선택적 **`AI로 다듬기`** 버튼과 수정 전 문구를 복원하는 **`되돌리기`** 버튼을 둔다.
- AI는 사용자가 입력하지 않은 원산지·품질·효능·인증 등을 임의로 만들어내지 않는다.
- 첫 퍼블리싱 단계에서는 버튼만 구현하고, 실제 AI API는 별도 승인 후 연결한다.

## 7. 코인 표시 정책(시연용)

- **기존 코인/토큰 운영 정책은 이번 MVP에서 폐기한다.**
- Figma 화면에 남아 있는 `남은 코인` 숫자는 디자인 확인을 위한 **임의의 고정 값**으로만 표시한다(예: `3개`).
- 코인 지급·차감·충전·서버 잔액 저장·이력 관리·부족 오류는 구현하지 않는다.
- AI 이미지 생성과 AI 문구 다듬기는 코인 숫자를 변경하지 않는다.
- UI에 코인 표기가 있어도 실제 이용권이나 과금 단위로 작동하지 않음을 코드와 문서에 명시한다.
- 향후 실제 이용량 제한이 필요하면 별도 정책을 정해 구현한다.

## 8. 마이페이지 정책

### 상품이 없는 경우

- **`시작하기` 버튼만 제공**한다. 클릭하면 상품 생성 화면으로 이동한다.
- 별도의 상품 목록, 안내 카드, 관리 메뉴, 수정·삭제 버튼은 제공하지 않는다(Figma의 공통 헤더 등은 유지 가능).

### 상품이 있는 경우

- **발행한 상품의 QR코드만 표시**한다.
- 상품 수정, 판매중지/재개, 삭제, 재발행, URL 복사, QR 다운로드 등 추가 기능은 이번 개발에서 제외한다.
- QR코드는 공개 상품 URL을 가리키며, 새로고침 후에도 동일 상품 URL을 유지한다.

### 상품 발행 규칙

- 단일 코드로 상품을 1개만 발행할 수 있다.
- 발행 후 재등록/교체 기능은 제공하지 않는다. 테스트 데이터 초기화가 필요하면 개발자가 서버에서 수동으로 처리한다.

## 9. 고객용 상품 페이지

- 단일 고정 템플릿을 모든 상품이 공유한다.
- 주요 요소: 상품 사진, 상품명, 가격, 규격/중량, 원산지, 소개 문구, 상호, 전화주문 버튼.
- 전화 버튼은 검증·정규화된 전화번호를 이용한 `tel:` 링크로 구현한다.
- 고객은 코드 인증이나 로그인 없이 접근한다.
- 공개 데이터에는 접속 코드, 세션, 내부 관리 필드를 포함하지 않는다.
- 모바일 화면에서 버튼이 명확하고 누르기 쉬워야 한다.
- 전화주문 서비스가 통신판매업 신고 등 법적 의무를 자동 면제하는 것은 아니므로, 법적 면제를 홍보 문구로 단정하지 않는다.

## 10. 기술 스택 및 구조

### 권장 스택

- **Vue 3 + Vite + JavaScript**
- **Vue Router**
- **일반 CSS** 및 Vue `<style scoped>` (필요한 곳에만)
- **Supabase Postgres + Storage**
- **Vercel** 호스팅 및 서버리스 API
- **QR코드 생성용 JS 라이브러리** (`qrcode` 등)
- OpenAI 이미지 편집 API: **서버에서만 호출**

기존 프로젝트의 선택과 충돌하면 무조건 새로 설치하지 말고 먼저 확인한다. 이번 프로젝트는 **TypeScript를 사용하지 않는다**. 기존 프로젝트가 TypeScript로 이미 설정되어 있다면 변경 전 사용자에게 확인한다.

### 권장 폴더 예시

위 폴더 구조는 예시이며 실제 프로젝트/서버리스 라우팅 규칙에 맞게 조정한다.

### DB 최소 모델(개념)

- `pages`: `id`, 상품/상점 필드, `image_path`, `published_at`, `created_at`
- 단일 비밀 접속 코드는 서버 측 환경변수 또는 별도의 안전한 저장소에서 검증한다. **복수 사용자용 `access_codes` 테이블은 필요하지 않다.**
- `coin_balance`, 코인 사용 이력, 코인 차감 관련 컬럼·테이블은 만들지 않는다.
- `ai_jobs`는 실제 AI API 연동 시 필요한 최소 작업 상태만 기록하도록 별도 검토한다(코인 필드 없음).

**DB 필수 제약:** 전체 서비스에서 발행된 상품은 최대 1개(단일 코드 기준). 프런트엔드뿐 아니라 서버·DB에서도 중복 발행을 방지한다. 공개 읽기는 발행된 상품의 허용 필드만 제공한다.

- Supabase RLS/Storage 정책을 명확히 설정한다. `service_role` 키는 브라우저에 절대 전달하지 않는다.
- 사진 업로드 파일 크기/형식 제한, 안전한 파일명, 접근 정책을 구현한다.
- 새로고침/다른 기기에서도 공개 URL이 작동해야 하므로 `localStorage`만으로 데이터를 보관하지 않는다.

## 11. Figma 공식 MCP 연동 및 퍼블리싱 원칙 — 중요

사용자는 디자이너이며 **레이아웃을 AI가 창의적으로 재해석하는 것보다 Figma의 세밀한 수치를 정확히 읽어 적용하는 것**을 중요하게 생각한다.

1. Figma 공식 MCP로 지정된 프레임을 읽는다. 접근할 수 없는 프레임이나 누락된 속성은 추측하지 말고 보고한다.
2. **바로 코딩하지 말고 먼저 `design-spec.md` 작성**:
   - 프레임 크기, 요소 계층, Auto Layout/Hug/Fill
   - width/height, padding, gap, 정렬
   - font family/size/weight/line-height/letter-spacing
   - color/opacity, border/radius, shadow
   - 이미지/아이콘 에셋 및 추출 경로
   - 실제 추출한 값과 추론한 값 명확히 구분
3. 사용자가 `design-spec.md`를 확인한 뒤 구현한다.
4. **디자인 수치를 임의로 변경하거나 '더 예쁘게' 수정하지 않는다.** 변경이 필요한 경우 이유와 변경값을 보고한다.
5. 원본 에셋을 우선 사용한다. 유사 아이콘이나 임의 이미지를 대체 삽입하지 않는다.
6. 지정된 Figma 기준 프레임(데스크톱 우선)에서 실제 브라우저 스크린샷을 촬영해 Figma 원본과 비교한다. 가능하다면 시각적 차이(간격, 크기, 타이포그래피)를 수정한다.
7. 디자인이 확정되기 전에는 기능 연동으로 넘어가지 않는다.
8. CSS는 가독성을 우선한다. 임의의 인라인 스타일과 불필요한 절대 위치 배치를 남발하지 않는다.
9. Figma에 아직 없는 화면은 임의 디자인을 확정하지 말고 간단한 구조적 플레이스홀더로 만들거나 디자인 제공을 요청한다.

## 12. 개발 순서 — 단계별 승인

### 1단계: 프로젝트 준비
- 기존 코드/환경 점검, Vue Router 및 기본 라우팅 구성
- Vue 3 + Vite + **JavaScript** 사용
- 필요한 환경변수 목록과 `.env.example` 작성(실제 코드·키 포함 금지)
- 목업 데이터와 최소 UI 골격만 생성
- **완료 후 보고하고 다음 단계 진행 여부 확인**

### 2단계: Figma 디자인 수치 추출 및 화면 퍼블리싱
- 사용자가 지정한 **첫 화면부터** Figma MCP로 분석해 `design-spec.md` 작성
- 승인 후 HTML/CSS/Vue 구현, 화면별로 순차 진행
- 브라우저 캡처로 Figma 대비 확인
- 코인 숫자는 고정 목업 값으로 표시
- 아직 DB/AI API 연결하지 않음

### 3단계: 단일 코드 인증 및 DB
- 서버에서 **비밀 코드 1개** 검증, 세션 발급
- Supabase 스키마/권한 정책, 상품 존재 여부 분기
- 상품 생성·조회·발행(수정/판매중지/삭제 제외)
- 중복 발행 차단 및 비인가 접근 검증

### 4단계: 발행·공개 페이지·QR
- 고유 URL, 공개 데이터 로딩
- QR코드 생성 및 마이페이지 표시
- 다른 기기에서 공개 URL 테스트

### 5단계: AI 이미지 및 소개글 다듬기
- 원본 사진 기반 이미지 편집, 원본 사용 옵션
- 입력한 문구 기반 AI 다듬기 및 되돌리기
- 서버 측 API 호출, 중복 요청 방지
- **코인 지급·차감·잔액 확인은 구현하지 않음**
- 실제 API 비용과 호출 횟수는 개발자가 별도 확인

### 6단계: 최종 점검
- 데스크톱/모바일 사용성, 오류·로딩 상태
- 무효 코드·세션 만료·권한 우회·중복 발행 테스트
- 상품 없음 → 시작하기, 상품 있음 → QR코드 표시 검증
- Vercel 배포 및 환경변수/보안 확인

## 13. 주요 수용 기준(완료 조건)

- 방문자는 랜딩에서 시작하기를 누르고 **단일 비밀 접속 코드**를 입력할 수 있다.
- 코드가 유효하면 마이페이지로 이동한다.
- 상품이 없으면 마이페이지에 **시작하기 버튼만**, 있으면 **생성된 QR코드만** 보인다.
- 상품을 발행하면 다른 휴대폰에서 URL/QR로 공개 페이지를 볼 수 있다.
- 전화주문 버튼이 올바른 번호를 호출한다.
- 같은 코드로 두 번째 상품을 발행할 수 없다.
- 수정·판매중지·삭제 UI 및 API가 없다.
- 남은 코인은 임의 숫자로 표시되며 AI 호출에도 변경되지 않는다.
- 코인 관련 DB/서버 차감 로직이 없다.
- AI API 키와 접속 코드가 클라이언트에 노출되지 않는다.
- Figma에서 확인된 디자인 수치와 실제 구현 수치의 차이가 기록·검토된다.

## 14. 아직 확정하지 않은 사항

- 최종 서비스 카피 및 Figma 링크·프레임 ID
- **단일 접속 코드**의 구체적 값·형식·길이·교체 방식(비밀값을 문서에 적지 않음)
- 남은 코인 UI에 표시할 임시 숫자(기본 예시: 3)
- AI 이미지 모델/해상도/품질/실패 처리 및 API 비용
- 지원 품목 최종 목록과 필수 입력값
- 업로드 이미지 제한 및 보존 기간
- AI 기능을 실제 연결할 시점
- 발행 후 상품 변경이 필요한 경우의 운영 절차(이번 MVP 범위 밖)
